# 학습한 것
## k6 (부하테스트)
- vus
동시에 실행되는 가상 사용 수
1vu는 1명의 사용자가 반복적으로 행동하는 것과 같음
실제 운영 서비스는 동시성이 중요하기 때문에 qps 보다 vus를 측정
1vu=1qps가 아님 (1명의 사용자가 여러 요청을 날릴 수 있기 때문)

- qps
Queries Per Second의 약자로 서버가 초당 처리 가능한 쿼리의 수를 의미하는 지표
시스템의 최대 처리 능력과 병목 지점을 파악하여 대규모 트래픽 발생 시 서버 다운을 방지하고 적절한 서버 자원을 설계하는 데 활용 가능

- duration
해당 부하를 얼마나 유지할 것인가에 대한 값
실무 기준으로 Baseline은 3~10분 / Spike는 30초~2분 / Soak는 1~6시간 / 배포 검증음 1~3분을 수행하고 안정 상태 진입 확인용 최소 시간은 5분
너무 짧으면 캐시나 커넥션 풀이 다 만들어지기 전의 데이터를 측정하기 때문에 평시의 사용자 경험을 테스트 할 수 없고
너무 길면 메모리 누수나 리소스 누적 문제를 측정하는 Soak 테스트가 되어버리기 때문에 적당한 5분의 길이가 가장 많이 사용된다.

- p95
테스트 시 평균은 거의 쓸모가 없는데 예를 들어
95개의 요청이 100ms가 걸렸고, 5개의 요청이 3초가 걸렸다고 했을 때
(95*100 + 5*3000) / 100 은 245ms로 문제가 없어보이지만, 5개의 요청은 3초가 걸렸기 때문에 체감 상 장애로 판정할 수 있다.
그래서 백분위수를 사용하는 데, 이 때 p95와 p99라는 기준으로 부하를 판단할 수 있다.
p95는 가장 느린 상위 5%의 요청을 제외한 최대 값이며, p99는 상위 1%를 제외한 최대값이다.
p95는 대부분의 사용자 경험을 테스트 할 수 있는 기준이며, p99는 최악에 가까운 사용자 경험을 테스트 할 수 있다.

- thresholds
k6의 부하테스트 합격/불합격을 판단하는 기준이 되는 옵션
http_req_duration은 요청의 시작부터 응답의 끝까지 걸린 시간을 체크하며, 체감 상 100ms 미만은 즉각 / 100~300ms는 빠름 / 300~500ms 허용 / 1s 이상은 느림 / 3s 이상은 이탈의 기준으로 본다. 500ms는 불만이 생기기 직전의 응답 시간이기 때문에 p95<500ms로 테스트 진행한다.
rate의 기준인 0.01은 네트워크는 항상 불완전하며 일시적인 실패가 존재하기 때문에 0.01로 기준을 잡고 테스트를 진행한다.

- slo (service level objective)
사용자 경험을 수치로 정의한 내부 운영 목표이며, sli같이 사용된다.
sli는 측정 기준, slo는 목표치이다
sli는 http_req_duration p95 (응답 시간에 대해 p95를 기준으로 측정)
slo는 p95<500ms (p95를 500ms와 비교)
slo가 없으면 '조금 느린 것 같다', '장애인가?' 라는 느낌으로 바라보게 되지만 slo가 있으면 'p95가 500ms를 넘었다', '에러율 1% 초과' 등 수치로 보여줄 수가 있다.
