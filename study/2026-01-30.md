# 쿠버네티스에 대한 이해
쿠버네티스의 다양한 개념들을 인지하기 전에, 쿠버네티스를 정의한다면 다양한 개념들이 왜 존재하고 어떤 역할을 하는지 알 수 있다.
쿠버네티스는 컨테이너를 실행하는 도구가 아니라 컨테이너 기반 애플리케이션의 상태를 '선언적으로 유지'하는 시스템

## 쿠버네티스의 핵심 철학 : Declarative & Control Loop
### Declarative : 선언적 시스템
명령형 (Imperative)
```md
서버 3개 띄워
죽으면 다시 띄워
업데이트할 땐 하나씩 바꿔
```

선언형 (Declarative)
```md
replicas: 3
image: app:v2
```

선언형은 desired state라 하여 상태를 선언하고, 해당 상태를 유지하도록 쿠버네티스가 작동한다.

### Control Loop
쿠버네티스는 아래의 행위를 계속 반복한다
```md
현재 상태 (current state)
      ↓
원하는 상태 (desired state)
      ↓
차이가 있으면 조정
```
Pod, Deployment, StatefulSet 전부 이 루프를 수행하기 위한 개념

## Pod : 컨테이너를 실행하는 최소 단위
Pod는 하나 이상의 컨테이너를 묶어 실행하는 쿠버네티스의 최소 실행 단위이다.
Pod 자체가 프로세스라기보단 환경의 단위로 봐야하고, 컨테이너들은 Pod 안에서 IP, localhost, 볼륨을 같이 공유한다.

Pod가 필요한 이유는, 컨테이너만으론 재시작 정책, 같은 네트워크의 묶음, 스토리지 공유, 상태관리 등이 어렵기 때문에 쿠버네티스는 Pod를 최소 단위로 지정하고 관리한다 (컨테이너 직접 관리 X)
Pod에 여러 개의 컨테이너를 넣는 경우는 Sidecar, Ambassador, Adapter 처럼 메인 애플리케이션과 같이 살아야 하는 컨테이너가 존재할 경우이다.

## Deployment : 무상태 애플리케이션의 운영 책임자
Deployment는 Pod의 생성, 업데이트, 스케일링, 복구를 관리하는 컨트롤러

### Deployment가 해결하는 문제
Deployment가 없으면 수동 재기동, 버전 변경 시 서비스 끊어짐, 스케일 조절 불가한 단점이 있다.
Deployment가 있으면 자동 재시작, Rolling Update로 인한 무중단 배포, Replica 관리로 스케일을 자동으로 조절 할 수 있다.

Deployment는 직접 Pod를 관리하지 않고, ReplicaSet을 통해 Pod의 갯수를 유지한다.

## StatefulSet : 상태를 기억하는 Pod
StatefulSet은 고정된 네트워크 id와 스토리지를 가지는 Pod를 관리하는 리소스
DB 컨테이너를 StatefulSet으로 사용하는 이유는, 재시작해도 데이터의 유지가 필요하며 고정된 endpoint가 필요하고, 먼저 배포되어야 애플리케이션 실행 시 오류가 없기 때문에 순서가 중요할 때 사용한다.

## Ingress : 외부 트래픽의 관문
Ingress는 http/https 요청을 클러스터 내부 서비스로 라우팅하는 규칙이다.

내부 Service만으로 부족한 이유는 포트 번호를 노출하며 https 설정이 번거로우며 도메인 기반 라우팅이 불가하다.
외부 트래픽을 받아내는 구조는 아래와 같으며 Ingress는 규칙을 설정하는 것이고 실제 구현체는 Ingress Controller가 된다.
```md
Client
 └─ Ingress Controller (Nginx)
      └─ Service
           └─ Pod
```

## ConfigMap / Secret : 이미지와 설정을 분리하는 이유
컨테이너를 생성하기 위한 이미지에 DB 비밀번호를 하드코딩하는 경우는 잘못된 예이며 설정은 외부에서 주입해줘야 한다.
ConfigMap은 환경 변수, 설정 파일, 로그 레벨 등 비민감 설정 정보를 위해 사용하고
Secret은 비밀번호, 토큰, 인증서처럼 민감 정보를 위해 사용한다.
