## 📚 Part 1: Kustomize 개념 (1시간)

### 1.1 Kustomize란?

Kustomize는 Kubernetes 매니페스트를 커스터마이징하는 도구로, kubectl에 내장되어 있습니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│  Kustomize 개념                                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Base + Overlay = 최종 매니페스트                                   │
│                                                                      │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │  Base (기본 설정)                                           │    │
│  │  ├── deployment.yaml (replicas: 1, image: nginx:1.24)      │    │
│  │  ├── service.yaml                                          │    │
│  │  └── kustomization.yaml                                    │    │
│  └─────────────────────────────────────────────────────────────┘    │
│            │                                                        │
│            ▼                                                        │
│  ┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐   │
│  │  Overlay: Dev   │   │ Overlay: Stage  │   │  Overlay: Prod  │   │
│  │  replicas: 1    │   │  replicas: 2    │   │  replicas: 5    │   │
│  │  image: :dev    │   │  image: :stage  │   │  image: :v1.0   │   │
│  │  resources: 작음│   │  resources: 중간│   │  resources: 큼  │   │
│  └─────────────────┘   └─────────────────┘   └─────────────────┘   │
│                                                                      │
│  장점:                                                              │
│  • 순수 YAML (템플릿 문법 없음)                                     │
│  • kubectl 내장 (별도 설치 불필요)                                  │
│  • 원본 유지하며 패치                                               │
│  • GitOps에 적합                                                    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 Helm vs Kustomize 비교

| 구분 | Helm | Kustomize |
|------|------|-----------|
| **방식** | 템플릿 (Go Template) | 패치/오버레이 |
| **문법** | {{ .Values.xxx }} | 순수 YAML |
| **학습 곡선** | 높음 | 낮음 |
| **패키지** | 가능 (Chart) | 불가능 |
| **번들 배포** | 가능 (tgz) | 불가능 |
| **kubectl** | 별도 설치 | 내장 |
| **YAML 가독성** | 낮음 (템플릿) | 높음 (순수) |
| **동적 생성** | 강력 | 제한적 |

```
언제 Helm?
- 복잡한 조건부 로직 필요
- 외부 Chart 사용
- 패키지 배포 필요

언제 Kustomize?
- 간단한 환경별 설정
- 기존 YAML 재사용
- kubectl만으로 충분
```

### 1.3 Kustomize 핵심 기능

```yaml
# kustomization.yaml 주요 필드
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

# 1. 리소스 포함
resources:
- deployment.yaml
- service.yaml
- ../base           # 다른 디렉토리 참조

# 2. 네임스페이스 설정
namespace: production

# 3. 이름 접두사/접미사
namePrefix: prod-
nameSuffix: -v1

# 4. 공통 레이블
commonLabels:
  app: myapp
  env: production

# 5. 공통 어노테이션
commonAnnotations:
  owner: devops-team

# 6. 이미지 변경
images:
- name: nginx
  newName: my-registry/nginx
  newTag: "1.25"

# 7. 레플리카 수 변경
replicas:
- name: deployment-name
  count: 5

# 8. ConfigMap/Secret 생성
configMapGenerator:
- name: app-config
  literals:
  - APP_ENV=production
secretGenerator:
- name: app-secret
  literals:
  - DB_PASSWORD=secret123

# 9. 패치 적용
patches:
- path: patch.yaml
- patch: |-
    - op: replace
      path: /spec/replicas
      value: 3
  target:
    kind: Deployment
    name: myapp
```

### 실습 2: Base 매니페스트 작성

```yaml
# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: nginx:1.24
        ports:
        - containerPort: 80
          name: http
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "200m"
            memory: "128Mi"
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 15
          periodSeconds: 20
```

```yaml
# base/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  selector:
    app: myapp
  ports:
  - name: http
    port: 80
    targetPort: 80
  type: ClusterIP
```

```yaml
# base/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
  APP_NAME: "My Application"
  LOG_LEVEL: "info"
```

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
- deployment.yaml
- service.yaml
- configmap.yaml

commonLabels:
  app.kubernetes.io/name: myapp
  app.kubernetes.io/managed-by: kustomize
```

## 🛠️ Part 3: 실습 - Overlay 구조 (1.5시간)

### 실습 4: Dev Overlay

```yaml
# overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

# Base 참조
resources:
- ../../base

# 네임스페이스 설정
namespace: dev

# 이름 접두사
namePrefix: dev-

# 레이블 추가
commonLabels:
  env: dev

# 레플리카 수 설정
replicas:
- name: myapp
  count: 1

# 이미지 태그 변경
images:
- name: nginx
  newTag: "1.24-alpine"

# ConfigMap 패치 (환경 변수 추가)
configMapGenerator:
- name: myapp-config
  behavior: merge
  literals:
  - APP_ENV=development
  - DEBUG=true

# 리소스 패치 (JSON Patch)
patches:
- patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources/requests/cpu
      value: "50m"
    - op: replace
      path: /spec/template/spec/containers/0/resources/limits/cpu
      value: "100m"
  target:
    kind: Deployment
    name: myapp
```

### 실습 6: Production Overlay

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
- ../../base

namespace: prod
namePrefix: prod-

commonLabels:
  env: prod
  tier: frontend

commonAnnotations:
  owner: devops-team
  slack-channel: "#prod-alerts"

replicas:
- name: myapp
  count: 5

images:
- name: nginx
  newName: my-registry.io/nginx
  newTag: "1.25-prod"

configMapGenerator:
- name: myapp-config
  behavior: merge
  literals:
  - APP_ENV=production
  - DEBUG=false
  - LOG_LEVEL=warn

# Secret 생성 (주의: 실제 값은 다른 방법으로 관리!)
secretGenerator:
- name: myapp-secret
  literals:
  - API_KEY=prod-api-key-xxxxx

patches:
- path: deployment-patch.yaml
- path: hpa.yaml
```

```yaml
# overlays/prod/deployment-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      containers:
      - name: myapp
        resources:
          requests:
            cpu: "500m"
            memory: "256Mi"
          limits:
            cpu: "1000m"
            memory: "512Mi"
        env:
        - name: API_KEY
          valueFrom:
            secretKeyRef:
              name: myapp-secret
              key: API_KEY
```

```yaml
# overlays/prod/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: prod-myapp
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

### 실습 8: 배포

```bash
# Dev 환경 배포
kubectl create namespace dev --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -k overlays/dev

# 확인
kubectl get all -n dev

# Staging 환경 배포
kubectl create namespace staging --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -k overlays/staging

# 확인
kubectl get all -n staging

# Production 환경 배포 (dry-run 먼저!)
kubectl apply -k overlays/prod --dry-run=client
kubectl create namespace prod --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -k overlays/prod

# 확인
kubectl get all -n prod
```

## 💡 면접 대비 핵심 포인트

### Q1: Kustomize의 장점은?
**A**: kubectl에 내장되어 별도 설치 불필요, 순수 YAML로 가독성 높음, Base/Overlay 구조로 환경별 설정 관리, GitOps에 적합

### Q2: Helm과 언제 사용하나요?
**A**: 복잡한 조건부 로직이나 패키지 배포가 필요하면 Helm, 간단한 환경별 설정이면 Kustomize를 사용합니다. ArgoCD에서는 둘 다 지원합니다.

### Q3: Strategic Merge Patch vs JSON Patch?
**A**: Strategic Merge Patch는 YAML 구조 유지하며 부분 수정, JSON Patch는 JSON Pointer로 정확한 경로 지정하여 수정합니다.
