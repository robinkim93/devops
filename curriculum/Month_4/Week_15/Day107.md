## 📚 Part 1: Git 브랜치 전략

### GitFlow vs Trunk-Based

```
┌────────────────────────────────────────────────────────────────────────────┐
│                        Git 브랜치 전략 비교                                 │
├────────────────────────────────────────────────────────────────────────────┤
│                                                                            │
│  GitFlow (복잡한 릴리스 관리)                                              │
│  ─────────────────────────────────────────────────────────────────────    │
│  main ─────●───────●───────●───────────────────────────────●──────        │
│            │       │       │                               │              │
│  release ──┼───────┼───●───┼───────────────────────────────┤              │
│            │       │   │   │                               │              │
│  develop ──●───●───●───●───●───●───●───●───────────────────●──────        │
│                │       │           │                                       │
│  feature ──────●───────●───────────●───────────────────────────────        │
│                                                                            │
│  Trunk-Based (빠른 배포, GitOps 권장)                                      │
│  ─────────────────────────────────────────────────────────────────────    │
│  main ─────●───●───●───●───●───●───●───●───●───●───●───●──────            │
│            │   │   │   │   │   │   │   │   │   │   │   │                  │
│  feature ──●───●───●───●───●───●───●───●───●───●───●───●──────            │
│            (짧은 수명의 feature 브랜치, 하루 내 머지)                       │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

### 토스플레이스 권장: Trunk-Based Development

```
권장 이유:
├── 빠른 배포 주기 (하루 수십 회)
├── 작은 변경 단위로 리스크 감소
├── GitOps와 자연스러운 통합
├── 코드 리뷰 부담 감소
└── CI/CD 파이프라인 단순화
```

### Commit Convention

```bash
# Conventional Commits
<type>(<scope>): <subject>

# Types
feat:     새로운 기능
fix:      버그 수정
docs:     문서 변경
style:    코드 포맷팅
refactor: 리팩토링
test:     테스트 추가
chore:    빌드/설정 변경

# 예시
feat(payment): 카드 결제 기능 추가
fix(auth): 토큰 만료 처리 버그 수정
chore(ci): GitHub Actions 워크플로우 개선
```

## 📚 Part 2: 환경 분리 전략

### Repository 구조

```
# 앱 코드와 인프라 코드 분리 (권장)

app-repo/                    # 애플리케이션 코드
├── src/
├── Dockerfile
├── tests/
└── .github/workflows/
    └── ci.yaml              # CI만 담당

infra-repo/                  # K8s 매니페스트 (GitOps)
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
├── overlays/
│   ├── dev/
│   │   ├── kustomization.yaml
│   │   └── patches/
│   ├── staging/
│   │   ├── kustomization.yaml
│   │   └── patches/
│   └── prod/
│       ├── kustomization.yaml
│       └── patches/
└── argocd/
    └── applications/
```

### Kustomize로 환경별 설정

```yaml
# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 1
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:latest
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
```

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: production

resources:
- ../../base

replicas:
- name: myapp
  count: 5

images:
- name: myapp
  newTag: v1.2.3

patches:
- path: patches/resources.yaml
```

```yaml
# overlays/prod/patches/resources.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      containers:
      - name: myapp
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: 1000m
            memory: 1Gi
```

### Image Tag 전략

| 환경 | 태그 방식 | 예시 |
|------|----------|------|
| Dev | Git SHA | `abc1234` |
| Staging | Git SHA | `abc1234` |
| Production | Semantic Version | `v1.2.3` |

```yaml
# CI에서 이미지 태그 업데이트 (GitHub Actions)
- name: Update Image Tag
  run: |
    cd infra-repo
    kustomize edit set image myapp=${REGISTRY}/myapp:${GITHUB_SHA:0:7}
    git commit -am "chore: update image to ${GITHUB_SHA:0:7}"
    git push
```

## 📚 Part 3: 배포 전략

### 1. Rolling Update (기본)

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 추가 Pod 수
      maxUnavailable: 0  # 동시 중단 Pod 수
```

### 2. Blue-Green (Istio)

```yaml
# VirtualService로 트래픽 전환
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: myapp
spec:
  hosts:
  - myapp
  http:
  - route:
    - destination:
        host: myapp
        subset: blue   # 100% → 0%
      weight: 0
    - destination:
        host: myapp
        subset: green  # 0% → 100%
      weight: 100
```

### 3. Canary (Istio)

```yaml
# 10% 트래픽만 새 버전으로
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  http:
  - route:
    - destination:
        host: myapp
        subset: stable
      weight: 90
    - destination:
        host: myapp
        subset: canary
      weight: 10
```

### 4. 롤백 전략

```bash
# ArgoCD 롤백
argocd app rollback myapp <revision>

# Git 롤백 (GitOps 방식)
git revert <commit-sha>
git push  # ArgoCD 자동 Sync

# Helm 롤백
helm rollback myapp 1

# kubectl 롤백
kubectl rollout undo deployment/myapp -n production
kubectl rollout history deployment/myapp -n production
```

## 📚 Part 4: Secret 관리

### Anti-Pattern (하지 말 것)

```yaml
# ❌ Git에 Secret 평문 저장 금지!
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
stringData:
  password: "my-secret-password"  # 노출됨!
```

### 권장 방식

| 방식 | 도구 | 설명 |
|------|------|------|
| Sealed Secrets | Bitnami | Git에 암호화된 Secret 저장 |
| External Secrets | ESO | Vault/AWS SM에서 동기화 |
| SOPS | Mozilla | 파일 암호화 |

```yaml
# Sealed Secret 예시
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-credentials
spec:
  encryptedData:
    password: AgBy3i4OJSWK+PiTySY...  # 암호화됨
```

```yaml
# External Secret 예시
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-credentials
  data:
  - secretKey: password
    remoteRef:
      key: secret/data/myapp/db
      property: password
```

## 📋 Best Practices 체크리스트

### CI 단계

| 항목 | 설명 |
|------|------|
| ☐ Lint & Format | 코드 품질 검사 |
| ☐ Unit Tests | 단위 테스트 |
| ☐ Security Scan | 취약점 검사 (trivy) |
| ☐ Build | 컨테이너 이미지 빌드 |
| ☐ Push | 레지스트리에 푸시 |

### CD 단계

| 항목 | 설명 |
|------|------|
| ☐ Staging 자동 배포 | main 머지 시 자동 |
| ☐ Integration Tests | 통합 테스트 실행 |
| ☐ Production 수동 승인 | 릴리스 매니저 승인 |
| ☐ Canary 배포 | 10% → 50% → 100% |
| ☐ Rollback 준비 | 즉시 롤백 가능 |
