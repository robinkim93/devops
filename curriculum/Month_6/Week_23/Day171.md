```
┌─────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────┤
```

### 3. 필수 명령어 정리

```bash
# ============================================
# 기본 워크플로우
# ============================================
terraform init          # 초기화 (Provider 다운로드)
terraform validate      # 문법 검증
terraform plan          # 변경사항 미리보기
terraform apply         # 실제 적용
terraform destroy       # 리소스 삭제

# ============================================
# Workspace
# ============================================
terraform workspace list          # 목록
terraform workspace new dev       # 생성
terraform workspace select prod   # 전환
terraform workspace show          # 현재 확인

# ============================================
# State 관리
# ============================================
terraform state list              # 리소스 목록
terraform state show RESOURCE     # 상세 정보
terraform state rm RESOURCE       # State에서 제거
terraform state mv OLD NEW        # 이름 변경
terraform state pull > backup     # 백업
terraform force-unlock LOCK_ID    # Lock 해제

# ============================================
# Import
# ============================================
terraform import aws_instance.example i-xxx
# Import Block (1.5+)
# import { to = aws_instance.example; id = "i-xxx" }
terraform plan -generate-config-out=generated.tf

# ============================================
# 디버깅
# ============================================
TF_LOG=DEBUG terraform apply
terraform apply -replace="aws_instance.web"
terraform plan -refresh-only
```

## 🛠️ Part 2: 종합 시나리오 연습 (1시간)

### 시나리오 1: 신규 프로젝트 IaC 구축

```
상황: 새로운 마이크로서비스를 위한 인프라를 구축해야 합니다.
요구사항:
- VPC (Public/Private Subnet)
- EKS Cluster
- RDS MySQL (Multi-AZ)
- dev/staging/prod 환경 분리
- GitOps CI/CD 파이프라인
```

**답변 가이드**:

```bash
# 1. 프로젝트 구조
terraform-project/
├── modules/           # 재사용 가능한 모듈
│   ├── vpc/
│   ├── eks/
│   └── rds/
├── environments/      # 환경별 구성
│   ├── dev/
│   ├── staging/
│   └── prod/
└── .github/workflows/ # CI/CD

# 2. 환경 분리 전략
- Workspace보다 Directory 구조 권장 (환경별 차이 큼)
- Backend는 환경별 별도 key 사용
- 공통 모듈은 버전 태깅으로 관리

# 3. CI/CD 워크플로우
- PR 생성 시 자동 Plan + 보안 스캔
- main 머지 시 dev 자동 배포
- prod는 수동 승인 필요

# 4. 보안 고려사항
- State 암호화 (S3 SSE-KMS)
- 시크릿은 Secrets Manager
- IAM Role 최소 권한
```

### 시나리오 2: 레거시 인프라 IaC 전환

```
상황: Console로 생성된 기존 AWS 리소스를 Terraform으로 관리하려 합니다.
현황: VPC 1개, EC2 10개, RDS 2개, S3 5개
```

**답변 가이드**:

```bash
# 1. 접근 방법
- Terraformer로 대량 Import 자동화
- 또는 Import Block으로 선언적 Import

# 2. 단계별 진행
Step 1: 의존성 분석 (VPC → Subnet → EC2 순서)
Step 2: Import Block 작성
Step 3: terraform plan -generate-config-out으로 코드 생성
Step 4: 생성된 코드 정리 및 모듈화
Step 5: terraform plan으로 "No changes" 확인

# 3. 주의사항
- 리소스 간 의존성 순서 중요
- Import 후 Plan 차이 꼼꼼히 확인
- lifecycle ignore_changes 필요 시 추가
```

### 시나리오 3: 프로덕션 장애 대응

```
상황: terraform apply 중 중단되어 일부 리소스만 생성되었습니다.
증상: State Lock 걸림, EKS는 생성됨, Node Group은 실패
```

**답변 가이드**:

```bash
# 1. 즉시 대응
- 추가 apply 시도 금지
- Lock 상태 확인

# 2. Lock 해제 (안전 확인 후)
aws dynamodb scan --table-name terraform-lock
terraform force-unlock LOCK_ID

# 3. 현재 상태 확인
terraform state list
terraform plan

# 4. 복구
- 실패한 리소스 원인 분석 (quota, permission 등)
- 원인 해결 후 terraform apply 재시도

# 5. 재발 방지
- CI/CD concurrency 설정
- timeout 설정 추가
- 롤백 전략 수립
```

## 🎤 Part 3: 면접 Q&A 연습 (1시간)

### Q1: Terraform State가 무엇이고 왜 중요한가요?

```
모범 답변:

"State는 Terraform이 관리하는 인프라의 현재 상태를 기록한 파일입니다.
세 가지 핵심 역할이 있습니다.

첫째, 리소스 매핑입니다. 코드의 리소스와 실제 클라우드 리소스를 연결합니다.
예를 들어 aws_instance.web이 실제로 i-abc123이라는 것을 기억합니다.

둘째, 성능 최적화입니다. 매번 클라우드 API를 호출하지 않고 State를 참조하여
빠르게 Plan을 수행합니다.

셋째, 메타데이터 저장입니다. 리소스 간 의존성 정보를 저장하여 올바른 순서로
생성/삭제를 수행합니다.

State 관리에서 중요한 점은:
- 원격 저장 (S3 + DynamoDB)으로 팀 협업 가능하게
- 암호화 필수 (민감 정보 포함)
- Lock으로 동시 수정 방지
- 버전 관리로 복구 가능하게 해야 합니다."
```

### Q2: Terraform Workspace와 Directory 구조의 차이점과 선택 기준은?

```
모범 답변:

"두 방식 모두 환경 분리에 사용됩니다.

Workspace는:
- 동일한 코드로 여러 State를 관리
- terraform.workspace 변수로 환경별 분기
- 코드 중복이 없어 유지보수 편리
- 단, 환경별 구성 차이가 크면 복잡해짐

Directory 구조는:
- 환경별 별도 디렉토리와 코드
- 완전한 분리로 유연성 높음
- 환경별 다른 Provider, 다른 리소스 구성 가능
- 단, 코드 중복 발생, 동기화 필요

선택 기준:
- 환경 간 차이가 적으면 (변수만 다르면) → Workspace
- 환경 간 구성이 많이 다르면 → Directory
- 팀 규모가 크고 독립적 관리 필요하면 → Directory

저는 실무에서 대부분 Directory 구조를 선호합니다. 프로덕션은 보수적으로,
개발은 실험적으로 운영하는 경우가 많아서 유연성이 필요하기 때문입니다."
```

### Q3: Terraform으로 기존 리소스를 관리하려면 어떻게 하나요?

```
모범 답변:

"terraform import 기능을 사용합니다. Terraform 1.5부터 Import Block이
도입되어 더 선언적으로 Import할 수 있습니다.

과정은:
1. 기존 리소스 정보 확인 (AWS Console/CLI)
2. Import Block 작성
3. terraform plan -generate-config-out으로 코드 자동 생성
4. 생성된 코드 정리
5. terraform plan으로 'No changes' 확인

대량 Import 시에는 Terraformer 도구를 활용하거나,
스크립트로 Import Block을 자동 생성합니다.

주의할 점:
- 의존성 순서 (VPC → Subnet → Instance)
- Import 후 Plan 차이 확인 필수
- Console 변경사항은 ignore_changes 검토"
```

### Q4: Terraform CI/CD 파이프라인을 어떻게 구성하시나요?

```
모범 답변:

"GitOps 원칙에 따라 Git을 Single Source of Truth로 사용합니다.

워크플로우:
1. Feature Branch에서 코드 작성
2. PR 생성 시 자동으로:
   - terraform fmt 검사
   - terraform validate
   - Checkov/tfsec 보안 스캔
   - terraform plan + PR 코멘트
3. 리뷰어가 Plan 결과 확인 후 Approve
4. main 머지 시:
   - dev 환경 자동 Apply
   - staging/prod는 수동 승인 후 Apply

핵심 설정:
- concurrency 설정으로 동시 Apply 방지
- Environment Protection Rules로 prod 보호
- State Lock으로 충돌 방지
- Drift Detection 스케줄 실행

이 방식의 장점은:
- 모든 변경이 Git에 기록되어 감사 용이
- 코드 리뷰로 실수 방지
- 롤백이 git revert로 간단"
```

### Q5: Terraform State Lock 충돌이 발생하면 어떻게 해결하나요?

```
모범 답변:

"먼저 Lock 정보를 확인합니다.

1. DynamoDB에서 Lock 조회:
   aws dynamodb scan --table-name terraform-lock

2. Lock 보유자와 생성 시간 확인:
   - 최근 생성이고 CI/CD 실행 중이면 → 대기
   - 오래되었거나 프로세스 없으면 → 좀비 Lock

3. 안전 확인 후 해제:
   terraform force-unlock LOCK_ID

재발 방지책:
- CI/CD에 concurrency 설정
- timeout 설정으로 좀비 방지
- Lock 모니터링 알림 구성

주의: force-unlock은 진행 중인 Apply가 없을 때만 사용해야 합니다.
동시 Apply는 State 손상을 유발할 수 있습니다."
```
