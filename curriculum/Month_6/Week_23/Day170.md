### 실습 1: State Lock 문제 해결 (20분)

**문제**: terraform apply 시 Lock 획득 실패

```bash
# 에러 메시지
# Error: Error acquiring the state lock
# 
# Error message: ConditionalCheckFailedException
# Lock Info:
#   ID:        a1b2c3d4-e5f6-7890-abcd-ef1234567890
#   Path:      s3://bucket/terraform.tfstate
#   Operation: OperationTypeApply
#   Who:       user@hostname
#   Version:   1.6.0
#   Created:   2024-01-15 10:30:00 UTC
```

**원인 분석 및 해결**:

```bash
# 1단계: Lock 정보 확인
aws dynamodb scan \
  --table-name terraform-lock \
  --filter-expression "contains(LockID, :path)" \
  --expression-attribute-values '{":path": {"S": "terraform.tfstate"}}' \
  --output table

# 예상 출력:
# +--------------------------------------+------------------------+
# |               LockID                 |          Info          |
# +--------------------------------------+------------------------+
# | bucket/terraform.tfstate-md5         | {"ID":"a1b2c3d4..."   |
# +--------------------------------------+------------------------+
```

```bash
# 2단계: Lock 보유자 확인
# Info 필드를 파싱하여 확인
aws dynamodb get-item \
  --table-name terraform-lock \
  --key '{"LockID": {"S": "bucket/terraform.tfstate"}}' \
  --query 'Item.Info.S' \
  --output text | jq .

# 예상 출력:
# {
#   "ID": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
#   "Operation": "OperationTypeApply",
#   "Who": "runner@github-actions-runner-123",
#   "Version": "1.6.0",
#   "Created": "2024-01-15T10:30:00.000Z",
#   "Path": "s3://bucket/terraform.tfstate"
# }
```

```bash
# 3단계: 판단
# - Created가 최근이고 GitHub Actions에서 실행 중이면 → 대기
# - Created가 오래되었거나 프로세스가 없으면 → Force Unlock

# Lock 생성 시간 확인 (30분 이상이면 좀비 가능성)
LOCK_TIME="2024-01-15T10:30:00.000Z"
CURRENT_TIME=$(date -u +%Y-%m-%dT%H:%M:%S.000Z)
echo "Lock created: $LOCK_TIME"
echo "Current time: $CURRENT_TIME"
```

```bash
# 4단계: 안전한 Force Unlock
# 주의: 진행 중인 Apply가 있으면 절대 실행하지 마세요!

# DynamoDB에서 직접 삭제
aws dynamodb delete-item \
  --table-name terraform-lock \
  --key '{"LockID": {"S": "bucket/terraform.tfstate"}}'

# 또는 Terraform 명령어 사용
terraform force-unlock a1b2c3d4-e5f6-7890-abcd-ef1234567890
```

```bash
# 5단계: 재발 방지 - CI/CD Concurrency 설정
# .github/workflows/terraform.yml
cat << 'EOF'
concurrency:
  group: terraform-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false  # 진행 중인 작업은 취소하지 않음
EOF
```

### 실습 2: Drift 감지 및 해결 (25분)

**문제**: terraform plan에서 예상치 못한 변경사항 감지

```bash
# Drift 감지
terraform plan -refresh-only

# 예상 출력:
# Note: Objects have changed outside of Terraform
# 
# aws_instance.web:
#   ~ instance_type = "t3.medium" -> "t3.large"  # Console에서 변경됨
```

**원인 분석**:

```
┌─────────────────────────────────────────────────────────────┐
│  Drift 발생 원인                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Console에서 직접 수정                                   │
│  2. 다른 Terraform 프로젝트에서 수정                        │
│  3. AWS CLI / SDK로 수정                                    │
│  4. Auto Scaling / 자동 복구 기능                           │
│  5. AWS 서비스 자체 업데이트                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**해결 방법**:

```bash
# 방법 1: State를 현재 상태로 업데이트 (변경 승인)
terraform apply -refresh-only

# 예상 출력:
# Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
# (State가 현재 인프라 상태로 업데이트됨)
```

```bash
# 방법 2: 코드를 현재 상태에 맞게 수정
# main.tf 수정
resource "aws_instance" "web" {
  instance_type = "t3.large"  # t3.medium → t3.large로 변경
  # ...
}

# 확인
terraform plan
# 예상 출력: No changes. Your infrastructure matches the configuration.
```

```bash
# 방법 3: 코드 기준으로 리소스 원복 (변경 거부)
terraform apply

# 예상 출력:
# aws_instance.web: Modifying... [id=i-xxx]
# aws_instance.web: Modifications complete after 30s
# (t3.large → t3.medium으로 다시 변경됨)
```

```bash
# 방법 4: 특정 속성 무시 (lifecycle)
resource "aws_instance" "web" {
  instance_type = "t3.medium"
  
  lifecycle {
    ignore_changes = [
      instance_type,  # Console 변경 무시
      tags["LastModifiedBy"],  # 자동 태그 무시
    ]
  }
}
```

**Drift Detection 자동화**:

```bash
# drift-report.sh
cat > drift-report.sh << 'EOF'
#!/bin/bash

echo "🔍 Drift Detection Report"
echo "========================="
echo "Generated: $(date)"
echo ""

for env in dev staging prod; do
  echo "📁 Environment: $env"
  cd environments/$env
  
  terraform init -backend=true -input=false > /dev/null 2>&1
  
  # Drift 확인
  PLAN_OUTPUT=$(terraform plan -refresh-only -no-color 2>&1)
  
  if echo "$PLAN_OUTPUT" | grep -q "Objects have changed"; then
    echo "  ⚠️  DRIFT DETECTED"
    echo "$PLAN_OUTPUT" | grep -A 5 "has changed"
  else
    echo "  ✅ No drift"
  fi
  
  cd ../..
  echo ""
done
EOF

chmod +x drift-report.sh
```

### 실습 3: 리소스 재생성 강제 (20분)

**문제**: 리소스가 손상되어 재생성이 필요한 경우

```bash
# 방법 1: taint (deprecated in 1.x)
terraform taint aws_instance.web

# 방법 2: replace (권장)
terraform apply -replace="aws_instance.web"

# 여러 리소스 동시 교체
terraform apply \
  -replace="aws_instance.web" \
  -replace="aws_instance.api"
```

**Plan만 확인**:

```bash
terraform plan -replace="aws_instance.web"

# 예상 출력:
# aws_instance.web must be replaced
# -/+ resource "aws_instance" "web" {
#       ~ id = "i-abc123" -> (known after apply)
#       ...
#     }
```

**모듈 내 리소스 교체**:

```bash
# 모듈 리소스 주소 확인
terraform state list | grep module.eks

# 특정 모듈 리소스 교체
terraform apply -replace="module.eks.aws_eks_node_group.main[\"general\"]"
```

### 실습 4: State 복구 (25분)

**문제**: State 파일 손상 또는 분실

```bash
# 시나리오 1: 로컬 State 손상
# terraform.tfstate.backup에서 복구
cp terraform.tfstate.backup terraform.tfstate

# 시나리오 2: S3 State 이전 버전 복구
# S3 버전 관리가 활성화되어 있어야 함
aws s3api list-object-versions \
  --bucket tossplace-terraform-state \
  --prefix dev/terraform.tfstate

# 특정 버전 다운로드
aws s3api get-object \
  --bucket tossplace-terraform-state \
  --key dev/terraform.tfstate \
  --version-id "abc123xyz" \
  terraform.tfstate.recovered

# 복구된 State 확인
terraform state list -state=terraform.tfstate.recovered
```

**State에서 리소스 제거**:

```bash
# 리소스가 이미 삭제되었지만 State에 남아있는 경우
terraform state rm aws_instance.deleted_manually

# 모듈 전체 제거
terraform state rm module.old_module
```

**State 이동**:

```bash
# 리소스 이름 변경 시
terraform state mv aws_instance.old_name aws_instance.new_name

# 모듈 간 이동
terraform state mv aws_instance.web module.web.aws_instance.main

# 다른 State 파일로 이동
terraform state mv -state-out=other.tfstate aws_instance.web
```

### 실습 5: 일반적인 에러 해결 (20분)

**에러 1: Provider 버전 충돌**

```bash
# 에러 메시지:
# Error: Failed to query available provider packages
# Could not retrieve the list of available versions for provider hashicorp/aws

# 해결: .terraform 삭제 후 재초기화
rm -rf .terraform .terraform.lock.hcl
terraform init
```

**에러 2: 순환 참조**

```bash
# 에러 메시지:
# Error: Cycle: aws_security_group.a, aws_security_group.b

# 원인 코드:
resource "aws_security_group" "a" {
  ingress {
    security_groups = [aws_security_group.b.id]  # B 참조
  }
}

resource "aws_security_group" "b" {
  ingress {
    security_groups = [aws_security_group.a.id]  # A 참조 → 순환!
  }
}

# 해결: 별도 규칙 리소스로 분리
resource "aws_security_group" "a" {
  name = "sg-a"
}

resource "aws_security_group" "b" {
  name = "sg-b"
}

resource "aws_security_group_rule" "a_from_b" {
  type                     = "ingress"
  security_group_id        = aws_security_group.a.id
  source_security_group_id = aws_security_group.b.id
  # ...
}

resource "aws_security_group_rule" "b_from_a" {
  type                     = "ingress"
  security_group_id        = aws_security_group.b.id
  source_security_group_id = aws_security_group.a.id
  # ...
}
```

**에러 3: API Rate Limit**

```bash
# 에러 메시지:
# Error: error reading EC2 instance: RequestLimitExceeded

# 해결 1: 재시도 설정
provider "aws" {
  region = "ap-northeast-2"
  
  # API 요청 재시도 설정
  retry_mode  = "standard"
  max_retries = 5
}

# 해결 2: 병렬 처리 제한
terraform apply -parallelism=5  # 기본값 10
```

**에러 4: 리소스 충돌**

```bash
# 에러 메시지:
# Error: creating Security Group: InvalidGroup.Duplicate: 
# The security group 'my-sg' already exists

# 원인: 이름이 같은 리소스가 이미 존재
# 해결 1: Import
terraform import aws_security_group.my_sg sg-abc123

# 해결 2: 이름 변경
resource "aws_security_group" "my_sg" {
  name = "my-sg-v2"  # 새 이름 사용
}
```

## 📊 Part 3: 장애 시나리오 실습 (20분)

### 시나리오: 프로덕션 리소스 실수로 삭제

```bash
# 상황: terraform destroy 잘못 실행으로 RDS 삭제

# 즉시 대응:
# 1. AWS Console에서 RDS 스냅샷 확인
aws rds describe-db-snapshots \
  --db-instance-identifier prod-db \
  --query 'DBSnapshots[0].DBSnapshotIdentifier'

# 2. 스냅샷에서 복구
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier prod-db-restored \
  --db-snapshot-identifier rds:prod-db-2024-01-15-10-00

# 3. Terraform State에 Import
terraform import module.rds.aws_db_instance.main prod-db-restored

# 4. 코드 수정하여 새 인스턴스 식별자와 매핑

# 재발 방지:
# - deletion_protection = true 설정
# - prevent_destroy 라이프사이클 추가
resource "aws_db_instance" "main" {
  deletion_protection = true
  
  lifecycle {
    prevent_destroy = true
  }
}
```
