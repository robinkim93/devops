## 📚 Part 1: 기술 면접 Q&A (2시간)

### 🔵 Kubernetes 질문

#### Q1: "Pod가 Pending 상태일 때 어떻게 트러블슈팅하나요?"

```
✅ 모범 답변:

"Pod가 Pending 상태일 때는 순차적으로 원인을 분석합니다.

첫째, kubectl describe pod으로 Events를 확인합니다.
주요 원인별로:

1. 리소스 부족
   - 'Insufficient cpu/memory' 이벤트 확인
   - kubectl describe nodes로 Allocatable 확인
   - 해결: 노드 추가 또는 리소스 request 조정

2. PVC 바인딩 실패
   - 'pod has unbound immediate PersistentVolumeClaims'
   - kubectl get pvc로 상태 확인
   - StorageClass 존재 여부, CSI Driver 확인

3. 스케줄링 불가
   - NodeSelector, Affinity, Taint 확인
   - 조건에 맞는 노드 존재 여부 확인

4. Image Pull 실패
   - 'ErrImagePull', 'ImagePullBackOff'
   - Secret 설정, 이미지 경로 확인

실제 프로젝트에서 EBS CSI Driver가 설치되지 않아 PVC가 바인딩되지 않는 
문제를 겪었고, addon 설치로 해결한 경험이 있습니다."
```

#### Q2: "HPA와 VPA의 차이점과 적절한 사용 케이스는?"

```
✅ 모범 답변:

"HPA는 Horizontal 스케일링으로 Pod 개수를 조절하고,
VPA는 Vertical 스케일링으로 Pod의 리소스 크기를 조절합니다.

HPA 적합 케이스:
- 트래픽 변동이 큰 웹 서비스
- Stateless 워크로드
- 빠른 스케일 아웃이 필요한 경우
- 토스플레이스 결제 API처럼 트래픽 스파이크 대응

VPA 적합 케이스:
- Stateful 워크로드 (DB, Cache)
- 초기 리소스 산정이 어려운 경우
- Batch 작업
- 리소스 최적화가 목적인 경우

주의점:
- HPA와 VPA를 CPU/Memory 동시 대상으로 사용하면 충돌
- VPA의 Recreate 모드는 Pod 재시작 발생

저는 프로젝트에서 일반 API는 HPA로, ML 모델 서빙은 VPA Recommend 모드로
리소스를 최적화했습니다."
```

### 🟣 Istio 질문

#### Q3: "Service Mesh를 도입하면 어떤 장점이 있나요?"

```
✅ 모범 답변:

"Service Mesh는 애플리케이션 레벨에서 처리하던 공통 기능을
인프라 레벨로 분리하여 개발자 생산성과 운영 효율성을 높입니다.

주요 장점:

1. 트래픽 관리
   - 카나리 배포, A/B 테스트를 코드 수정 없이 구현
   - 애플리케이션 로직과 배포 전략 분리

2. 보안
   - mTLS로 서비스 간 통신 자동 암호화
   - AuthorizationPolicy로 세밀한 접근 제어

3. 관측성
   - 모든 서비스 간 통신 자동 메트릭 수집
   - 분산 추적 (Jaeger)으로 요청 흐름 파악

4. 복원력
   - Circuit Breaker로 장애 격리
   - Retry, Timeout 정책 중앙 관리

단점도 있습니다:
- Sidecar로 인한 리소스 오버헤드 (약 10-20%)
- 운영 복잡도 증가
- 디버깅 난이도 증가

토스플레이스처럼 많은 마이크로서비스가 있는 환경에서는
이점이 단점을 충분히 상쇄한다고 생각합니다."
```

#### Q4: "카나리 배포를 Istio로 어떻게 구현하나요?"

```
✅ 모범 답변:

"VirtualService의 weight를 사용하여 트래픽 비율을 조절합니다.

apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  hosts: [myservice]
  http:
  - route:
    - destination:
        host: myservice
        subset: stable
      weight: 90
    - destination:
        host: myservice
        subset: canary
      weight: 10

단계별 진행:
1. 새 버전 배포 (version: canary 레이블)
2. weight 10%로 시작
3. 메트릭 모니터링 (에러율, 레이턴시)
4. 문제없으면 점진적으로 비율 증가
5. 100%에서 stable로 전환

추가로 헤더 기반 라우팅도 가능합니다:
- 특정 사용자만 새 버전 테스트
- QA 팀에게만 canary 노출

프로젝트에서 Argo Rollouts와 연동하여
자동 Progressive Delivery를 구현했습니다."
```

### 🟢 CI/CD 질문

#### Q5: "GitOps의 장점은 무엇인가요?"

```
✅ 모범 답변:

"GitOps는 Git을 Single Source of Truth로 사용하여
인프라와 애플리케이션을 관리하는 방법론입니다.

핵심 장점:

1. 감사 추적성 (Auditability)
   - 모든 변경이 Git 커밋으로 기록
   - 누가, 언제, 왜 변경했는지 명확
   - 컴플라이언스 대응 용이

2. 선언적 관리 (Declarative)
   - '어떻게'가 아닌 '무엇'을 정의
   - 코드 = 현재 상태

3. 셀프 힐링 (Self-Healing)
   - ArgoCD가 drift를 자동 감지/수정
   - 수동 변경 방지

4. 롤백 용이
   - git revert로 즉시 롤백
   - 이전 상태로 완벽 복구

5. 협업 개선
   - PR 기반 변경 → 코드 리뷰 강제
   - 인프라 변경도 팀 리뷰

토스플레이스에서 여러 팀이 독립적으로 배포하면서도
일관된 프로세스를 유지하는 데 GitOps가 적합하다고 생각합니다."
```

### 🟠 모니터링 질문

#### Q6: "SLI/SLO/SLA의 차이점은?"

```
✅ 모범 답변:

"세 개념은 서비스 수준 관리의 계층입니다.

SLI (Service Level Indicator) - 측정 지표
- 실제 측정 가능한 메트릭
- 예: 응답시간 P99, 에러율, 가용성
- PromQL: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

SLO (Service Level Objective) - 내부 목표
- SLI에 대한 목표 값
- 예: P99 응답시간 < 200ms, 가용성 > 99.9%
- 팀 내부 운영 기준

SLA (Service Level Agreement) - 외부 약속
- 고객과의 계약
- SLO보다 보수적으로 설정
- 미달 시 패널티 (환불 등)

Error Budget 개념:
- SLO 99.9% = 월 43분 다운타임 허용
- 남은 예산 범위 내에서 실험/배포 가능

저는 프로젝트에서 프론트엔드 P99 200ms, 
백엔드 P99 500ms SLO를 정의하고
Grafana 대시보드에서 Error Budget을 추적했습니다."
```

#### Q7: "Thanos가 왜 필요한가요?"

```
✅ 모범 답변:

"Prometheus의 한계를 해결합니다.

Prometheus 한계:
1. 단일 노드 → 확장성 제한
2. 로컬 스토리지 → 장기 저장 어려움
3. 단일 클러스터 → 멀티 클러스터 뷰 불가

Thanos 해결책:

1. 장기 저장 (Object Storage)
   - S3에 메트릭 저장
   - 비용 효율적인 장기 보관

2. Global View
   - 여러 Prometheus의 메트릭 통합 쿼리
   - 멀티 클러스터 환경에 필수

3. 고가용성
   - Prometheus 인스턴스 중복 제거
   - 다운타임 없이 쿼리

4. 다운샘플링
   - 오래된 데이터는 해상도 낮춤
   - 저장 비용 절감

아키텍처:
Prometheus → Thanos Sidecar → S3
              ↓
        Thanos Query ← Thanos Store Gateway

토스플레이스처럼 여러 EKS 클러스터를 운영하는 환경에서
Thanos로 통합 모니터링하는 것이 필수적입니다."
```

### 🔴 장애 대응 질문

#### Q8: "실제 프로덕션 장애 대응 경험을 말씀해주세요."

```
✅ 모범 답변 (STAR 기법):

Situation (상황):
"새벽 3시에 알림을 받았습니다. 결제 API의 P99 응답시간이 
평소 200ms에서 2초로 급증했습니다."

Task (과제):
"원인을 빠르게 파악하고 서비스를 정상화해야 했습니다."

Action (행동):
"1. Grafana 대시보드에서 메트릭 확인
   - 03:00부터 급격한 지연 시작
   
2. Jaeger에서 트레이스 분석
   - DB 쿼리 지연이 주 원인

3. RDS CloudWatch 확인
   - CPU 100%, 커넥션 수 급증

4. 원인 파악
   - 배치 작업이 프로덕션 DB에 직접 쿼리 중

5. 즉시 조치
   - 배치 작업 중지
   - 커넥션 풀 설정 조정

6. 근본 해결
   - 배치 작업을 읽기 전용 복제본으로 이전
   - DB 커넥션 알림 추가"

Result (결과):
"30분 내 정상화되었고, 재발 방지를 위해 배치 작업 격리와
모니터링 강화를 구현했습니다. 이후 유사 장애가 발생하지 않았습니다."
```

## 📚 Part 2: 문화 적합성 면접 준비 (1시간)

### Q: "왜 토스플레이스에 지원하셨나요?"

```
✅ 모범 답변:

"세 가지 이유가 있습니다.

첫째, 기술적 도전입니다.
오프라인 결제 시장을 혁신하는 과정에서 대규모 트래픽을 안정적으로
처리하는 인프라를 구축하는 것이 매력적입니다.

둘째, DevOps 문화입니다.
'개발자들이 스스로 빠르고 안전하게 배포할 수 있는 환경'이라는 
목표가 제가 생각하는 DevOps의 본질과 일치합니다.
단순히 운영하는 것이 아니라 플랫폼을 만드는 역할에 끌렸습니다.

셋째, 성장 가능성입니다.
초기 멤버로 합류하여 인프라 설계부터 참여할 수 있다는 점이
큰 기회라고 생각합니다. 오너십을 가지고 일할 수 있는 환경을 원합니다."
```

### Q: "어떤 DevOps 엔지니어가 되고 싶으신가요?"

```
✅ 모범 답변:

"동료 개발자들의 생산성을 높이는 DevOps 엔지니어가 되고 싶습니다.

구체적으로는:

1. 플랫폼 제공자
   - 개발자가 인프라를 신경 쓰지 않고 개발에 집중할 수 있도록
   - Self-service 플랫폼 구축

2. 문제 해결사
   - 장애 상황에서 빠르게 원인을 파악하고 해결
   - 근본 원인 분석으로 재발 방지

3. 자동화 전문가
   - 반복 작업의 자동화
   - 휴먼 에러 제거

4. 지식 공유자
   - 팀 내 DevOps 문화 전파
   - 문서화와 교육

궁극적으로는 '인프라 걱정 없이 빠르게 실험하고 배포할 수 있다'는 
피드백을 받는 것이 목표입니다."
```
