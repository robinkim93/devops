# 📅 Day 124: Recording Rules로 쿼리 최적화

## 🎯 오늘의 목표

> **토스플레이스 연결점**: "대규모 환경에서 Prometheus 쿼리 성능 최적화"

대시보드에서 복잡한 PromQL 쿼리를 실행할 때마다 Prometheus에 부하가 걸립니다. **Recording Rules**를 사용하면 복잡한 쿼리를 미리 계산해두어 **응답 속도를 개선**하고 **Prometheus 부하를 줄일** 수 있습니다.

## 📚 Part 1: 핵심 개념 (40분)

### Recording Rules란?

```
┌─────────────────────────────────────────────────────────────┐
│  Recording Rules = 쿼리 결과의 캐싱                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ❌ Recording Rules 없이:                                    │
│                                                             │
│  Grafana 대시보드 새로고침할 때마다:                         │
│  → 복잡한 쿼리 실행                                          │
│  → 수천 개 시계열 스캔                                       │
│  → 매번 2-3초 소요                                           │
│  → Prometheus CPU 급증                                       │
│                                                             │
│  ✅ Recording Rules 사용:                                    │
│                                                             │
│  30초마다 백그라운드에서:                                    │
│  → 복잡한 쿼리 미리 계산                                     │
│  → 결과를 새 메트릭으로 저장                                 │
│                                                             │
│  대시보드 조회 시:                                           │
│  → 미리 계산된 메트릭만 읽기                                 │
│  → 즉시 응답 (<100ms)                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 언제 Recording Rules를 사용하나?

```
┌─────────────────────────────────────────────────────────────┐
│  Recording Rules 사용 기준                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 자주 사용되는 쿼리                                       │
│     - 대시보드에서 반복 조회                                 │
│     - 여러 Alert에서 동일 쿼리 참조                          │
│                                                             │
│  2. 계산 비용이 높은 쿼리                                    │
│     - 많은 시계열에 대한 집계 (sum, avg)                     │
│     - histogram_quantile 계산                               │
│     - 여러 메트릭 조인                                       │
│                                                             │
│  3. 복잡한 표현식                                            │
│     - 중첩된 함수 호출                                       │
│     - 여러 단계의 계산                                       │
│                                                             │
│  ❌ 사용하지 않아도 되는 경우:                                │
│     - 단순 메트릭 조회                                       │
│     - 가끔 실행하는 일회성 쿼리                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Recording Rules 네이밍 컨벤션

```
┌─────────────────────────────────────────────────────────────┐
│  권장 네이밍: level:metric:operations                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  예시:                                                       │
│                                                             │
│  job:http_requests:rate5m                                   │
│   │        │          │                                     │
│   │        │          └── 연산: 5분 rate                     │
│   │        └───────────── 메트릭: http_requests             │
│   └────────────────────── 레벨: job (집계 수준)             │
│                                                             │
│  namespace:container_memory:sum                             │
│      │           │          │                               │
│      │           │          └── 연산: sum                   │
│      │           └───────────── 메트릭: container_memory    │
│      └───────────────────────── 레벨: namespace             │
│                                                             │
│  cluster:node_cpu:ratio                                     │
│     │       │       │                                       │
│     │       │       └── 연산: 비율 계산                      │
│     │       └──────────── 메트릭: node_cpu                  │
│     └──────────────────── 레벨: cluster (전체)              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### PrometheusRule CRD 구조

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: myapp-recording-rules
  namespace: monitoring
  labels:
    release: prometheus          # ⚠️ 필수: Prometheus가 이 label로 찾음
spec:
  groups:
  - name: myapp.rules            # 그룹 이름
    interval: 30s                # 계산 주기 (기본: global)
    rules:
    # Recording Rule (record: 사용)
    - record: job:http_requests:rate5m
      expr: sum(rate(http_requests_total[5m])) by (job)
      labels:
        team: platform           # 추가 레이블 (선택)
```

### Recording Rule vs Alerting Rule

| 구분 | Recording Rule | Alerting Rule |
|------|---------------|---------------|
| 키워드 | `record:` | `alert:` |
| 목적 | 쿼리 결과 저장 | 조건 충족 시 알림 |
| 출력 | 새 메트릭 생성 | Alertmanager로 전송 |
| 사용 | 대시보드, 다른 쿼리 | 알림 |

### 실습 1: 기본 Recording Rule 생성 (25분)

**목표**: HTTP 요청률을 미리 계산하는 규칙 생성

```bash
# 1. PrometheusRule 생성
cat << 'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: http-recording-rules
  namespace: monitoring
  labels:
    release: prometheus
    app: kube-prometheus-stack
spec:
  groups:
  - name: http.rules
    interval: 30s
    rules:
    # 1. 서비스별 요청률
    - record: job:http_requests:rate5m
      expr: sum(rate(http_requests_total[5m])) by (job)
    
    # 2. 상태 코드별 요청률
    - record: job:http_requests_by_status:rate5m
      expr: sum(rate(http_requests_total[5m])) by (job, code)
    
    # 3. 에러 요청률 (5xx)
    - record: job:http_requests_errors:rate5m
      expr: sum(rate(http_requests_total{code=~"5.."}[5m])) by (job)
EOF

# 2. 생성 확인
kubectl get prometheusrules -n monitoring http-recording-rules

# 3. 상세 확인
kubectl describe prometheusrules -n monitoring http-recording-rules
```

**예상 출력**:
```
NAME                    AGE
http-recording-rules    10s
```

**목표**: 미리 계산된 메트릭 사용

### 실습 4: 에러율 Recording Rule (25분)

**목표**: 복잡한 에러율 계산을 미리 수행

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: error-rate-rules
  namespace: monitoring
  labels:
    release: prometheus
    app: kube-prometheus-stack
spec:
  groups:
  - name: error_rate.rules
    interval: 30s
    rules:
    # 1. 에러율 (에러 수 / 전체 수)
    - record: job:http_error_rate:ratio
      expr: |
        sum(rate(http_requests_total{code=~"5.."}[5m])) by (job)
        /
        sum(rate(http_requests_total[5m])) by (job)
    
    # 2. 성공률 (1 - 에러율)
    - record: job:http_success_rate:ratio
      expr: |
        1 - (
          sum(rate(http_requests_total{code=~"5.."}[5m])) by (job)
          /
          sum(rate(http_requests_total[5m])) by (job)
        )
    
    # 3. 가용성 (성공률 * 100)
    - record: job:http_availability:percent
      expr: job:http_success_rate:ratio * 100
EOF
```

**쿼리 사용**:
```promql
# 복잡한 원본 쿼리 대신
job:http_error_rate:ratio

# 가용성 확인 (99.9% SLA 체크)
job:http_availability:percent < 99.9
```

### 실습 5: 리소스 메트릭 Recording Rules (25분)

**목표**: CPU/메모리 사용률 사전 계산

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: resource-recording-rules
  namespace: monitoring
  labels:
    release: prometheus
    app: kube-prometheus-stack
spec:
  groups:
  - name: resource.rules
    interval: 30s
    rules:
    # 1. 네임스페이스별 CPU 사용량
    - record: namespace:container_cpu_usage:sum
      expr: |
        sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) by (namespace)
    
    # 2. 네임스페이스별 메모리 사용량
    - record: namespace:container_memory_usage:sum
      expr: |
        sum(container_memory_usage_bytes{container!=""}) by (namespace)
    
    # 3. 노드별 CPU 사용률 (%)
    - record: instance:node_cpu_utilization:ratio
      expr: |
        1 - avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
    
    # 4. 노드별 메모리 사용률 (%)
    - record: instance:node_memory_utilization:ratio
      expr: |
        1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
    
    # 5. Pod별 재시작 횟수 (1시간)
    - record: namespace:pod_restarts:increase1h
      expr: |
        sum(increase(kube_pod_container_status_restarts_total[1h])) by (namespace, pod)
EOF
```

**활용 예시**:
```promql
# 대시보드에서 빠르게 조회
instance:node_cpu_utilization:ratio * 100   # 노드 CPU %

# 알림에서 재사용
namespace:container_memory_usage:sum > 10737418240  # 10GB 초과
```

### 실습 6: Recording Rule 체이닝 (10분)

**목표**: Recording Rule 결과를 다른 Rule에서 참조

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: chained-rules
  namespace: monitoring
  labels:
    release: prometheus
    app: kube-prometheus-stack
spec:
  groups:
  - name: chained.rules
    rules:
    # 1단계: 기본 계산
    - record: job:http_requests:rate5m
      expr: sum(rate(http_requests_total[5m])) by (job)
    
    # 2단계: 1단계 결과 사용 (체이닝)
    - record: cluster:http_requests:rate5m
      expr: sum(job:http_requests:rate5m)  # ← Recording Rule 참조
    
    # 3단계: 비율 계산
    - record: job:http_requests:ratio_to_cluster
      expr: |
        job:http_requests:rate5m / ignoring(job) group_left cluster:http_requests:rate5m
EOF
```

**주의**: 체이닝된 Rule은 **같은 그룹 내에서 순서대로** 정의해야 함

## 📊 Part 3: 모범 사례 및 주의사항

### Recording Rules 모범 사례

```
┌─────────────────────────────────────────────────────────────┐
│  ✅ 모범 사례                                                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 명확한 네이밍                                            │
│     level:metric:operations 형식 준수                        │
│                                                             │
│  2. 적절한 interval                                          │
│     - 기본: 30s ~ 1m                                         │
│     - 너무 짧으면 Prometheus 부하 증가                       │
│                                                             │
│  3. 레이블 보존                                              │
│     필요한 레이블은 by() 절에 포함                           │
│                                                             │
│  4. 문서화                                                   │
│     annotations에 목적 설명 추가                             │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│  ❌ 피해야 할 것                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 과도한 Recording Rules                                   │
│     → 저장 공간 낭비, 관리 복잡성                            │
│                                                             │
│  2. 너무 높은 카디널리티                                     │
│     → by (instance, pod, container) 등 모든 레이블 포함 X   │
│                                                             │
│  3. 사용하지 않는 Rule 방치                                  │
│     → 정기적으로 정리                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
