## 🎯 개요

### 프로젝트 목표

이 프로젝트는 다음 목표를 달성하기 위해 설계되었습니다:

1. **프로덕션 수준의 모니터링**: 실제 운영 환경에서 사용 가능한 모니터링 스택
2. **Golden Signals 기반 관찰성**: Traffic, Errors, Latency, Saturation 모니터링
3. **SLO/Error Budget 관리**: 서비스 수준 목표 추적 및 가시화
4. **장기 메트릭 저장**: Thanos를 통한 90일+ 메트릭 보관
5. **자동화된 알림**: 프로액티브한 장애 감지 및 알림

| 요건 | 구현 내용 | 상태 |

| Prometheus, Thanos, Grafana | 메트릭 수집, 장기 저장, 시각화 | ✅ |
| 모니터링 시스템 구축/운영 | ServiceMonitor, Alert Rules | ✅ |
| 대규모 분산 환경 | 멀티 클러스터 지원 (Thanos) | ✅ |
| 장애 대응 자동화 | Alertmanager, Slack 연동 | ✅ |

## ✨ 주요 기능

### 메트릭 수집

- **ServiceMonitor/PodMonitor**: 애플리케이션 자동 발견 및 스크래핑
- **Recording Rules**: 자주 사용하는 쿼리 사전 계산
- **Federation**: 멀티 클러스터 메트릭 수집

### 시각화

- **Golden Signals Dashboard**: Traffic, Errors, Latency, Saturation
- **SLO Dashboard**: 가용성 목표 및 Error Budget 추적
- **K8s Overview**: 클러스터, 노드, Pod 상태

### 알림

- **임계값 기반 Alert**: 에러율, 지연 시간, 리소스 사용량
- **SLO 기반 Alert**: Error Budget 소진 경고
- **그룹핑 및 라우팅**: 심각도별 알림 채널

### 장기 저장

- **Thanos**: 90일+ 메트릭 장기 보관
- **다운샘플링**: 저장 효율화
- **글로벌 뷰**: 여러 클러스터 메트릭 통합 조회

### 설치

```bash
# 1. 저장소 클론
git clone https://github.com/username/monitoring-portfolio.git
cd monitoring-portfolio

# 2. Namespace 생성
kubectl create namespace monitoring

# 3. Prometheus Stack 설치
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install prometheus prometheus-community/kube-prometheus-stack \
  -n monitoring \
  -f helm/values/prometheus-values.yaml

# 4. (선택) Thanos 설치
helm repo add bitnami https://charts.bitnami.com/bitnami

## 🚨 알림

### Alert 규칙

| Alert 이름 | 조건 | Severity | 대응 |
|-----------|------|----------|------|
| HighErrorRate | 에러율 > 5% for 5m | Critical | 즉시 확인, 롤백 검토 |
| HighLatency | P99 > 1s for 5m | Critical | 리소스 확인, 스케일링 |
| ErrorBudgetLow | Budget < 20% | Warning | 배포 주의 |
| PodCrashLooping | 재시작 > 3회/5m | Warning | 로그 확인 |
| NodeNotReady | 노드 NotReady > 5m | Critical | 노드 상태 확인 |

### Alertmanager 설정

```yaml
# alertmanager/alertmanager.yaml
global:
  slack_api_url: 'https://hooks.slack.com/services/xxx/yyy/zzz'

route:
  receiver: 'slack-notifications'
  group_by: ['alertname', 'severity']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - match:
        severity: critical
      receiver: 'slack-critical'
      repeat_interval: 1h

receivers:
  - name: 'slack-notifications'
    slack_configs:
      - channel: '#alerts'
        send_resolved: true
        
  - name: 'slack-critical'
    slack_configs:
      - channel: '#alerts-critical'
        send_resolved: true
```

### 3.1 Architecture.md

```markdown
# 시스템 아키텍처

## 개요

이 문서는 Kubernetes 모니터링 시스템의 상세 아키텍처를 설명합니다.

## 컴포넌트

### Prometheus Operator

Prometheus Operator는 Kubernetes 네이티브 방식으로 Prometheus를 관리합니다.

**주요 CRD:**
- `Prometheus`: Prometheus 인스턴스 정의
- `ServiceMonitor`: 서비스 스크래핑 설정
- `PodMonitor`: Pod 직접 스크래핑 설정
- `PrometheusRule`: Alert 및 Recording Rule

**선택 이유:**
- Kubernetes 리소스로 선언적 관리
- 자동 설정 재로드
- 고가용성 구성 용이

### Thanos

Thanos는 Prometheus의 확장성과 장기 저장을 담당합니다.

**컴포넌트:**
- Sidecar: Prometheus 옆에서 데이터 업로드
- Store: S3에서 데이터 조회
- Query: 통합 쿼리 인터페이스
- Compactor: 데이터 압축 및 다운샘플링

**데이터 흐름:**
```
Prometheus → Sidecar → S3
                ↑
Query ← Store ←─┘
```

### Grafana

시각화 및 대시보드 플랫폼입니다.

**특징:**
- 다양한 데이터소스 지원
- 대시보드 as Code
- 알림 기능 (Unified Alerting)

### Alertmanager

Alert 라우팅, 그룹핑, 알림 전송을 담당합니다.

**기능:**
- 중복 제거 (Deduplication)
- 그룹핑 (Grouping)
- 억제 (Inhibition)
- 침묵 (Silence)

## 설계 결정

### ADR-001: Prometheus Operator 사용

**상태:** 승인됨

**컨텍스트:**
Kubernetes에서 Prometheus를 운영하는 방법 선택 필요

**결정:**
Prometheus Operator 사용

**이유:**
- CRD 기반의 선언적 관리
- 커뮤니티 활성화
- 자동 설정 갱신

### ADR-002: Thanos를 장기 저장소로 사용

**상태:** 승인됨

**컨텍스트:**
90일 이상 메트릭 보관 필요

**결정:**
Thanos + S3 사용

**이유:**
- 무제한 저장 기간
- 비용 효율적 (S3)
- 멀티 클러스터 지원

## 확장성

### 수평 확장

- Prometheus: Sharding (hashmod)
- Thanos Query: 복제본 추가
- Alertmanager: Cluster 모드

### Grafana 대시보드 백업

```bash
#!/bin/bash
# backup-dashboards.sh

GRAFANA_URL="http://localhost:3000"
GRAFANA_USER="admin"
GRAFANA_PASS="password"
BACKUP_DIR="./dashboard-backups/$(date +%Y%m%d)"

mkdir -p $BACKUP_DIR

# 대시보드 목록 조회
dashboards=$(curl -s -u $GRAFANA_USER:$GRAFANA_PASS \
  "$GRAFANA_URL/api/search?type=dash-db" | jq -r '.[].uid')

for uid in $dashboards; do
  echo "Backing up dashboard: $uid"
  curl -s -u $GRAFANA_USER:$GRAFANA_PASS \
    "$GRAFANA_URL/api/dashboards/uid/$uid" > "$BACKUP_DIR/$uid.json"
done

echo "Backup completed: $BACKUP_DIR"
```

# 트러블슈팅 가이드

## 일반적인 문제

### 1. Prometheus Target이 DOWN

**증상**: Targets 페이지에서 일부 Target이 DOWN 상태

**원인 및 해결**:

| 원인 | 확인 방법 | 해결 |
|------|----------|------|
| Pod 미실행 | `kubectl get pods` | Pod 상태 확인 |
| 잘못된 selector | ServiceMonitor yaml | selector 수정 |
| 포트 불일치 | Service/ServiceMonitor | 포트 확인 |
| 네트워크 정책 | NetworkPolicy | 정책 허용 추가 |

```bash
# 디버깅
kubectl get servicemonitor <name> -n monitoring -o yaml
kubectl get endpoints <service> -n <namespace>
```

### 2. 메트릭이 보이지 않음

**증상**: Grafana 대시보드에 "No Data"

**확인 순서**:
1. Prometheus에서 메트릭 직접 조회
2. 데이터소스 연결 확인
3. 쿼리 시간 범위 확인

```bash
# Prometheus에서 메트릭 존재 확인
curl "http://localhost:9090/api/v1/query?query=up" | jq
```

### 3. Alertmanager 알림 미발송

**증상**: Alert는 Firing인데 Slack 알림 없음

**확인 순서**:
1. Alertmanager 설정 확인
2. Slack webhook URL 테스트
3. 라우팅 규칙 확인

```bash
# Alertmanager 설정 확인
kubectl get secret alertmanager-prometheus-kube-prometheus-alertmanager \
  -n monitoring -o jsonpath='{.data.alertmanager\.yaml}' | base64 -d

# Slack webhook 직접 테스트
curl -X POST -H 'Content-type: application/json' \
  --data '{"text":"Test message"}' \
  https://hooks.slack.com/services/xxx/yyy/zzz
```

### 4. Prometheus OOM

**증상**: Prometheus Pod가 OOMKilled로 재시작

**해결**:
1. 메모리 limit 증가
2. retention 기간 단축
3. Recording Rule로 쿼리 최적화
4. 불필요한 메트릭 drop

```yaml
# 메모리 증설
prometheus:
  prometheusSpec:
    resources:
      limits:
        memory: 16Gi
```
```
