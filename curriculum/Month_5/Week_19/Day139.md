# 📅 Day 139: 알림 전략 - 효과적인 알림 설계

## 🎯 오늘의 목표

> **토스플레이스 연결점**: "알림 피로 없이 중요한 문제만 빠르게 인지"

알림이 너무 많으면 **알림 피로(Alert Fatigue)**로 인해 정작 중요한 알림을 놓치게 됩니다. 효과적인 알림 전략은 **필요한 알림만**, **적절한 사람에게**, **적시에** 전달하는 것입니다.

## 📚 Part 1: 핵심 개념 (1시간)

### 알림 피로란?

```
┌─────────────────────────────────────────────────────────────┐
│  Alert Fatigue (알림 피로)                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  증상:                                                       │
│  - 알림이 와도 "또 저거지" 하고 무시                        │
│  - 중요한 알림을 노이즈에 묻혀 놓침                          │
│  - On-call이 스트레스와 번아웃                               │
│                                                             │
│  원인:                                                       │
│  - 너무 많은 알림                                            │
│  - 액션이 필요 없는 알림                                     │
│  - 같은 알림 반복                                            │
│  - 새벽에 불필요한 알림                                      │
│                                                             │
│  결과:                                                       │
│  - 진짜 장애 발생 시 대응 지연                               │
│  - 팀 사기 저하                                              │
│  - 서비스 품질 저하                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 좋은 알림의 조건

```
┌─────────────────────────────────────────────────────────────┐
│  알림 품질 체크리스트                                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Actionable (조치 가능)                                   │
│     ✅ "결제 서비스 에러율 5% 초과 - DB 연결 확인 필요"     │
│     ❌ "CPU 사용률 변동 중"                                  │
│                                                             │
│  2. Relevant (관련성)                                        │
│     ✅ 담당 서비스의 문제                                    │
│     ❌ 관계없는 서비스 알림                                  │
│                                                             │
│  3. Timely (적시성)                                          │
│     ✅ 문제 발생 즉시                                        │
│     ❌ 이미 해결된 후                                        │
│                                                             │
│  4. Unique (고유성)                                          │
│     ✅ 새로운 문제                                           │
│     ❌ 같은 문제 반복 알림                                   │
│                                                             │
│  5. Complete (완전성)                                        │
│     ✅ 무엇이, 어디서, 언제, 왜                              │
│     ❌ "서버 이상" (정보 부족)                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Severity 레벨 설계

```
┌─────────────────────────────────────────────────────────────┐
│  4-Level Severity System                                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  🔴 P1 (Critical) - 즉각 대응 필요                          │
│     - 서비스 완전 중단                                       │
│     - 데이터 손실 위험                                       │
│     - 응답: 15분 이내                                        │
│     - 채널: PagerDuty (전화)                                │
│     - 예: "결제 서비스 다운", "DB 연결 불가"                │
│                                                             │
│  🟠 P2 (High) - 신속 대응 필요                               │
│     - 심각한 성능 저하                                       │
│     - 일부 기능 장애                                         │
│     - 응답: 30분 이내                                        │
│     - 채널: Slack #alerts-urgent                            │
│     - 예: "P99 지연 2초 초과", "에러율 1% 초과"             │
│                                                             │
│  🟡 P3 (Medium) - 업무 시간 내 대응                          │
│     - 경미한 성능 저하                                       │
│     - 예방적 조치 필요                                       │
│     - 응답: 4시간 이내                                       │
│     - 채널: Slack #alerts                                   │
│     - 예: "디스크 80% 초과", "인증서 30일 이내 만료"        │
│                                                             │
│  🟢 P4 (Low) - 정보성                                        │
│     - 트렌드 파악용                                          │
│     - 조치 불필요                                            │
│     - 응답: 필요시                                           │
│     - 채널: Slack #alerts-info                              │
│     - 예: "트래픽 50% 증가", "새 버전 배포 완료"            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 실습 1: 알림 분류 및 정리 (30분)

**목표**: 기존 알림을 검토하고 정리

```bash
# 현재 알림 규칙 목록
kubectl get prometheusrules -n monitoring -o custom-columns=NAME:.metadata.name,RULES:.spec.groups[*].rules[*].alert
```

**알림 분류 체크리스트**:

| 알림 | Actionable? | Severity | 유지/삭제 |
|------|-------------|----------|----------|
| HighCPU > 80% | ✅ 스케일 필요 | P3 | 유지 |
| MemoryUsage 변동 | ❌ 정보성 | - | 삭제 |
| PodRestart > 3회 | ✅ 조사 필요 | P2 | 유지 |
| TargetDown | ✅ 복구 필요 | P2 | 유지 |

### 실습 2: 효과적인 알림 메시지 작성 (20분)

**목표**: 알림 annotations 개선

```yaml
# ❌ 나쁜 예
annotations:
  summary: "Error"
  description: "Something is wrong"

# ✅ 좋은 예
annotations:
  summary: "High error rate on {{ $labels.service }}"
  description: |
    에러율: {{ $value | humanizePercentage }}
    서비스: {{ $labels.service }}
    네임스페이스: {{ $labels.namespace }}
    시작 시간: {{ $labels.startsAt }}
    
    예상 원인:
    - DB 연결 문제
    - 외부 API 장애
    - 리소스 부족
  runbook_url: "https://wiki.company.com/runbook/high-error-rate"
  dashboard_url: "https://grafana.company.com/d/xxx?var-service={{ $labels.service }}"
```

### 실습 3: Alertmanager 라우팅 최적화 (30분)

**목표**: Severity별 라우팅 설정

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: alertmanager-config
  namespace: monitoring
stringData:
  alertmanager.yaml: |
    global:
      resolve_timeout: 5m
    
    route:
      receiver: 'default'
      group_by: ['alertname', 'severity', 'service']
      group_wait: 30s
      group_interval: 5m
      repeat_interval: 4h
      routes:
        # P1: Critical - 즉시 전화
        - match:
            severity: critical
          receiver: 'pagerduty-critical'
          group_wait: 10s
          repeat_interval: 1h
          continue: true  # 슬랙에도 전송
        
        # P1: Critical - Slack에도
        - match:
            severity: critical
          receiver: 'slack-critical'
          group_wait: 10s
        
        # P2: High - 긴급 슬랙
        - match:
            severity: warning
          receiver: 'slack-warning'
          routes:
            # 업무 시간 외 Critical만 전화
            - match:
                severity: warning
              receiver: 'slack-warning'
              mute_time_intervals:
                - outside-business-hours
        
        # P3/P4: 일반 슬랙
        - match_re:
            severity: info|none
          receiver: 'slack-info'
          repeat_interval: 24h
    
    receivers:
      - name: 'default'
        slack_configs:
          - channel: '#alerts'
      
      - name: 'pagerduty-critical'
        pagerduty_configs:
          - service_key: '<PAGERDUTY_KEY>'
            severity: critical
      
      - name: 'slack-critical'
        slack_configs:
          - channel: '#alerts-critical'
            color: 'danger'
            title: '🚨 {{ .Status | toUpper }}: {{ .CommonLabels.alertname }}'
            text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'
      
      - name: 'slack-warning'
        slack_configs:
          - channel: '#alerts-warning'
            color: 'warning'
      
      - name: 'slack-info'
        slack_configs:
          - channel: '#alerts-info'
    
    inhibit_rules:
      # Critical이면 Warning 억제
      - source_match:
          severity: 'critical'
        target_match:
          severity: 'warning'
        equal: ['alertname', 'service']
    
    time_intervals:
      - name: outside-business-hours
        time_intervals:
          - weekdays: ['saturday', 'sunday']
          - times:
              - start_time: '00:00'
                end_time: '09:00'
              - start_time: '18:00'
                end_time: '24:00'
```

### 실습 4: Runbook 작성 (20분)

**목표**: 알림별 대응 절차 문서화

```markdown
# Runbook: HighErrorRate

## 알림 정보
- **알림명**: HighErrorRate
- **Severity**: Critical
- **SLO 영향**: 가용성 SLO 위반

## 증상
- HTTP 5xx 에러율이 1% 초과

## 영향
- 사용자 요청 실패
- 매출 손실 가능

## 즉각 대응 (5분 이내)

### 1. 현재 상태 확인
```promql
sum(rate(http_requests_total{status=~"5.."}[5m])) by (service) / sum(rate(http_requests_total[5m])) by (service)
```

### 2. 최근 변경 확인
- 배포 이력: `kubectl rollout history deployment/<service> -n production`
- 설정 변경: Git 커밋 로그

### 3. 로그 확인
```logql
{namespace="production", service="<service>"} |= "error" | json
```

## 일반적인 원인과 해결

### 원인 1: DB 연결 문제
- **확인**: DB 메트릭, 커넥션 풀
- **해결**: Pod 재시작, DB 스케일업

### 원인 2: 외부 API 장애
- **확인**: 외부 API 상태 페이지
- **해결**: Circuit breaker 활성화, fallback

### 원인 3: 메모리 부족
- **확인**: `kubectl top pods`
- **해결**: HPA 트리거, 수동 스케일

## 에스컬레이션
- 15분 이상 해결 안 될 시: @team-lead
- 30분 이상: @engineering-manager
```

## 📊 Part 3: 알림 품질 측정

### 알림 KPI

| 메트릭 | 계산 | 목표 |
|--------|------|------|
| **MTTA** (Mean Time To Acknowledge) | 알림 ~ 인지 시간 | < 5분 |
| **MTTR** (Mean Time To Resolve) | 알림 ~ 해결 시간 | < 30분 |
| **알림 노이즈율** | 무시된 알림 / 전체 | < 10% |
| **실제 장애 탐지율** | 탐지 장애 / 실제 장애 | > 95% |

### 주간 알림 리뷰

```
매주 검토할 것:
1. 가장 많이 발생한 알림 TOP 5
2. 무시된 알림 목록
3. 알림 없이 발생한 장애
4. On-call 피드백
```
