## 📚 Part 1: 핵심 개념 (1시간)

### SLI/SLO/SLA 관계

```
┌─────────────────────────────────────────────────────────────┐
│  SLI → SLO → SLA                                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  SLI (Service Level Indicator)                              │
│  "무엇을 측정할 것인가?"                                     │
│  - 정량적 측정 지표                                          │
│  - 예: 요청 중 200ms 이내 응답 비율                          │
│                                                             │
│         ↓                                                   │
│                                                             │
│  SLO (Service Level Objective)                              │
│  "목표가 무엇인가?"                                          │
│  - SLI의 목표값                                              │
│  - 예: "월간 99.9%의 요청이 200ms 이내 응답"                 │
│                                                             │
│         ↓                                                   │
│                                                             │
│  SLA (Service Level Agreement)                              │
│  "약속을 어기면 어떻게 되는가?"                              │
│  - 계약 (위반 시 환불/보상)                                  │
│  - 예: "99.9% 미달 시 서비스 크레딧 제공"                    │
│                                                             │
│  ※ 일반적으로 SLA < SLO (여유 두기)                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### SLI 선정 원칙

```
┌─────────────────────────────────────────────────────────────┐
│  좋은 SLI의 조건                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 사용자 경험과 직결                                       │
│     ✅ 좋음: 요청 응답 시간                                  │
│     ❌ 나쁨: 서버 CPU 사용률                                 │
│                                                             │
│  2. 측정 가능                                                │
│     ✅ 좋음: 200ms 이내 응답 비율                            │
│     ❌ 나쁨: "체감 속도"                                     │
│                                                             │
│  3. 비율로 표현                                              │
│     ✅ 좋음: 성공 요청 / 전체 요청 = 99.9%                   │
│     ❌ 나쁨: 평균 응답시간 123ms                             │
│                                                             │
│  4. 의미 있는 기간                                           │
│     ✅ 좋음: 지난 30일간                                     │
│     ❌ 나쁨: "최근 데이터"                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 일반적인 SLI 유형

| 서비스 유형 | SLI | 측정 방법 |
|------------|-----|----------|
| **API 서비스** | 가용성 | 성공 요청 / 전체 요청 |
| | 지연시간 | P99 < 200ms인 요청 비율 |
| **웹사이트** | 가용성 | HTTP 200 응답 비율 |
| | 성능 | 페이지 로드 < 3초 비율 |
| **데이터 파이프라인** | 신선도 | 데이터 지연 < 10분 비율 |
| | 정확성 | 정확한 레코드 비율 |
| **스토리지** | 내구성 | 데이터 손실 없는 비율 |
| | 처리량 | 목표 IOPS 달성 비율 |

### Error Budget (에러 예산)

```
┌─────────────────────────────────────────────────────────────┐
│  Error Budget = 허용 가능한 실패                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  SLO: 99.9% 가용성                                          │
│  → Error Budget: 0.1% 다운타임 허용                         │
│                                                             │
│  월간 기준:                                                  │
│  30일 × 24시간 × 60분 × 0.1% = 43.2분/월 다운타임 허용      │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  월 시작                                월 끝        │   │
│  │  |============================================|       │   │
│  │  |████████████████████|                      |       │   │
│  │       사용한 예산 (20분)    남은 예산 (23.2분)        │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Error Budget 활용:                                         │
│  - 예산 남음 → 새 기능 배포, 실험 가능                       │
│  - 예산 소진 → 안정성 작업만, 배포 중단                      │
│                                                             │
│  → 개발팀과 운영팀의 균형점 제공                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### SLO 수준별 다운타임

| SLO | 월간 다운타임 | 연간 다운타임 | 적합한 서비스 |
|-----|-------------|--------------|--------------|
| 99% | 7.2시간 | 3.65일 | 내부 도구 |
| 99.5% | 3.6시간 | 1.83일 | 비핵심 서비스 |
| 99.9% | 43.2분 | 8.76시간 | **대부분 서비스** |
| 99.95% | 21.6분 | 4.38시간 | 핵심 서비스 |
| 99.99% | 4.3분 | 52.6분 | 결제, 인증 |

## 🛠️ Part 2: 실습 (1시간 30분)

### 실습 1: SLI 쿼리 작성 (30분)

**목표**: 주요 SLI를 PromQL로 표현

**가용성 SLI**:
```promql
# 성공 요청 비율 (지난 30일)
sum(increase(http_requests_total{status!~"5.."}[30d]))
/
sum(increase(http_requests_total[30d]))

# 또는 Recording Rule로 사전 계산
# record: job:http_availability:ratio30d
```

**지연시간 SLI**:
```promql
# 200ms 이내 응답 비율 (지난 30일)
sum(increase(http_request_duration_seconds_bucket{le="0.2"}[30d]))
/
sum(increase(http_request_duration_seconds_count[30d]))
```

**가용성 SLI (5분 단위)**:
```promql
# 실시간 가용성
sum(rate(http_requests_total{status!~"5.."}[5m])) by (service)
/
sum(rate(http_requests_total[5m])) by (service)
```

### 실습 2: Recording Rules로 SLI 저장 (20분)

**목표**: SLI를 효율적으로 계산하고 저장

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: sli-recording-rules
  namespace: monitoring
  labels:
    release: prometheus
spec:
  groups:
  - name: sli.rules
    interval: 30s
    rules:
    # 가용성 SLI (5분)
    - record: service:http_availability:ratio5m
      expr: |
        sum(rate(http_requests_total{status!~"5.."}[5m])) by (service)
        /
        sum(rate(http_requests_total[5m])) by (service)
    
    # 지연시간 SLI (200ms 이내)
    - record: service:http_latency_200ms:ratio5m
      expr: |
        sum(rate(http_request_duration_seconds_bucket{le="0.2"}[5m])) by (service)
        /
        sum(rate(http_request_duration_seconds_count[5m])) by (service)
    
    # 지연시간 SLI (500ms 이내)
    - record: service:http_latency_500ms:ratio5m
      expr: |
        sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m])) by (service)
        /
        sum(rate(http_request_duration_seconds_count[5m])) by (service)
    
    # 에러 예산 소모율 (월간)
    - record: service:error_budget_consumption:ratio
      expr: |
        1 - (service:http_availability:ratio5m / 0.999)
EOF
```

### 실습 3: SLO 대시보드 생성 (30분)

**목표**: SLO 현황을 시각화

**Row 1: 현재 SLO 상태**

```promql
# Panel 1: 가용성 (Stat)
service:http_availability:ratio5m{service="$service"} * 100
# Unit: percent
# Thresholds: SLO 기준 (99.9 = 녹색)

# Panel 2: SLO 달성 여부 (Stat)
# Value mapping: >= 0.999 → "✅ SLO Met", < 0.999 → "❌ SLO Breach"
service:http_availability:ratio5m{service="$service"}

# Panel 3: 지연시간 SLO (Stat)
service:http_latency_200ms:ratio5m{service="$service"} * 100
```

**Row 2: Error Budget**

```promql
# Panel 4: Error Budget 남은 비율 (Gauge)
# SLO 99.9% 기준 에러 예산
(0.001 - (1 - service:http_availability:ratio5m{service="$service"})) / 0.001 * 100
# Unit: percent
# Min: 0, Max: 100
# Thresholds: 50 (yellow), 20 (red)

# Panel 5: Error Budget 소모 트렌드 (Time series)
# 지난 7일간 에러 예산 소모량 트렌드
1 - service:http_availability:ratio5m{service="$service"}
```

**Row 3: SLO 히스토리**

```promql
# Panel 6: 가용성 히스토리 (Time series)
service:http_availability:ratio5m{service="$service"} * 100
# + SLO 라인: 99.9 (Threshold)

# Panel 7: 지연시간 히스토리 (Time series)
service:http_latency_200ms:ratio5m{service="$service"} * 100
```

### 실습 4: SLO 위반 알림 설정 (20분)

**목표**: SLO 위반 시 알림

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: slo-alerts
  namespace: monitoring
  labels:
    release: prometheus
spec:
  groups:
  - name: slo.alerts
    rules:
    # 가용성 SLO 위반
    - alert: AvailabilitySLOBreach
      expr: service:http_availability:ratio5m < 0.999
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "Availability SLO breach on {{ $labels.service }}"
        description: "Availability is {{ $value | humanizePercentage }} (SLO: 99.9%)"
    
    # Error Budget 50% 소모
    - alert: ErrorBudget50Consumed
      expr: |
        (0.001 - (1 - service:http_availability:ratio5m)) / 0.001 < 0.5
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Error budget 50% consumed on {{ $labels.service }}"
    
    # Error Budget 90% 소모 (긴급)
    - alert: ErrorBudget90Consumed
      expr: |
        (0.001 - (1 - service:http_availability:ratio5m)) / 0.001 < 0.1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "Error budget nearly exhausted on {{ $labels.service }}"
        description: "Only {{ $value | humanizePercentage }} of error budget remaining"
    
    # 지연시간 SLO 위반
    - alert: LatencySLOBreach
      expr: service:http_latency_200ms:ratio5m < 0.999
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Latency SLO breach on {{ $labels.service }}"
```

## 📊 Part 3: 실무 SLO 예시

### 토스플레이스 스타일 SLO

```
┌─────────────────────────────────────────────────────────────┐
│  결제 서비스 SLO                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  SLI 1: 가용성                                               │
│  - 정의: 성공적으로 처리된 결제 요청 비율                    │
│  - 측정: HTTP 2xx / 전체 요청                               │
│  - SLO: 월간 99.99% (4.3분 다운타임)                        │
│                                                             │
│  SLI 2: 지연시간                                             │
│  - 정의: 200ms 이내 응답 비율                               │
│  - 측정: P99 < 200ms인 요청 비율                            │
│  - SLO: 월간 99.9%                                          │
│                                                             │
│  Error Budget:                                              │
│  - 가용성: 4.3분/월 (0.01%)                                 │
│  - 예산 소진 시: 배포 중단, 안정성 작업만                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  API Gateway SLO                                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  SLI: 가용성 99.9%, 지연시간 P99 < 100ms                    │
│  Error Budget: 43.2분/월                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### SLO 설정 시 주의사항

```
1. 너무 높은 SLO 피하기
   - 99.999% (5 nines)는 월 26초 다운타임
   - 현실적으로 달성하기 매우 어려움
   
2. 측정 가능해야 함
   - "빠른 응답" ❌ → "P99 < 200ms" ✅
   
3. 팀이 동의해야 함
   - 개발팀, 운영팀, 비즈니스팀 합의
   
4. 정기적으로 검토
   - 분기별 SLO 적절성 검토
   - 너무 쉬우면 상향, 너무 어려우면 하향
```
