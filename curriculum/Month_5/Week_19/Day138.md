## 🛠️ Part 2: 실습 - 장애 시나리오 (2시간)

### 시나리오 1: 높은 에러율 (40분)

**상황**: 알림 수신 - "payment-service 에러율 5% 초과"

**Step 1: 현재 상태 확인**

```promql
# 에러율 확인
sum(rate(http_requests_total{service="payment-service", status=~"5.."}[5m]))
/
sum(rate(http_requests_total{service="payment-service"}[5m]))

# 예상: 0.08 (8%) ← 정상 0.1% 대비 매우 높음
```

**Step 2: 에러 상세 분석**

```promql
# 에러 코드별 분류
sum(rate(http_requests_total{service="payment-service", status=~"5.."}[5m])) by (status)

# 예상:
# status="500" → 0.02
# status="503" → 0.06 ← 503이 대부분!

# 503 = Service Unavailable → 백엔드 문제 가능성
```

**Step 3: 시간 축 확인**

```promql
# 언제부터 시작됐나?
# Grafana에서 시간 범위 넓혀서 확인 (Last 6 hours)
sum(rate(http_requests_total{service="payment-service", status=~"5.."}[5m]))

# 특정 시점부터 급증 확인
# → 그 시점에 무슨 일이 있었나?
```

**Step 4: 로그 확인**

```logql
# 에러 로그 조회
{namespace="production", app="payment-service"} |= "error" | json

# 503 관련 로그
{namespace="production", app="payment-service"} |= "503"

# 예상 로그:
# "Connection refused to database"
# "Connection pool exhausted"
```

**Step 5: 의존성 확인**

```promql
# DB 연결 수
pg_stat_activity_count{datname="payment"}

# DB 쿼리 응답 시간
histogram_quantile(0.99, sum(rate(pg_query_duration_seconds_bucket[5m])) by (le))

# 예상: DB 커넥션 풀 고갈 발견!
```

**해결**:
```bash
# 임시 조치: Pod 재시작으로 커넥션 풀 리셋
kubectl rollout restart deployment payment-service -n production

# 근본 해결: 커넥션 풀 크기 조정, 커넥션 타임아웃 설정
```

### 시나리오 2: 높은 지연시간 (40분)

**상황**: "API 응답이 느려요" - P99 응답시간 2초 (평소 200ms)

**Step 1: 지연시간 확인**

```promql
# P99 응답시간
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket{service="api-gateway"}[5m])) by (le)
)

# 예상: 2.3 (2.3초)

# 엔드포인트별 분리
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket{service="api-gateway"}[5m])) by (le, path)
)

# 예상:
# path="/api/users" → 0.15s (정상)
# path="/api/orders" → 2.5s ← 특정 엔드포인트만 느림!
```

**Step 2: 해당 서비스 분석**

```promql
# orders 서비스 내부 지연
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket{service="order-service"}[5m])) by (le)
)

# 외부 호출 지연
histogram_quantile(0.99,
  sum(rate(external_request_duration_seconds_bucket{service="order-service"}[5m])) by (le, target)
)

# 예상: target="inventory-service" → 2.1s ← 원인 발견!
```

**Step 3: 근본 원인 추적**

```promql
# inventory-service CPU
sum(rate(container_cpu_usage_seconds_total{pod=~"inventory-.*"}[5m])) by (pod)
/
sum(kube_pod_container_resource_limits{pod=~"inventory-.*", resource="cpu"}) by (pod)

# 예상: 0.95 (95%) ← CPU 포화!

# Pod 수 확인
count(kube_pod_status_phase{namespace="production", pod=~"inventory-.*", phase="Running"})

# 예상: 2개 (HPA 설정 확인 필요)
```

**해결**:
```bash
# 임시 조치: 수동 스케일 아웃
kubectl scale deployment inventory-service --replicas=5 -n production

# 근본 해결: HPA 설정 검토, 리소스 limits 조정
```

### 시나리오 3: Pod 재시작 반복 (40분)

**상황**: 알림 - "user-service Pod이 1시간에 5번 재시작"

**Step 1: 재시작 현황 확인**

```promql
# 재시작 횟수
sum(increase(kube_pod_container_status_restarts_total{namespace="production", pod=~"user-service.*"}[1h])) by (pod)

# 마지막 종료 이유
kube_pod_container_status_last_terminated_reason{namespace="production", pod=~"user-service.*"}

# 예상: reason="OOMKilled" ← 메모리 부족으로 종료!
```

**Step 2: 메모리 사용 분석**

```promql
# 현재 메모리 사용량
sum(container_memory_usage_bytes{namespace="production", pod=~"user-service.*", container!=""}) by (pod)

# 메모리 limit
sum(kube_pod_container_resource_limits{namespace="production", pod=~"user-service.*", resource="memory"}) by (pod)

# 사용률
sum(container_memory_usage_bytes{pod=~"user-service.*", container!=""}) by (pod)
/
sum(kube_pod_container_resource_limits{pod=~"user-service.*", resource="memory"}) by (pod)

# 예상: 0.98 (98%) ← limit에 거의 도달
```

**Step 3: 메모리 트렌드 확인**

```promql
# 시간에 따른 메모리 증가 (메모리 누수 확인)
container_memory_usage_bytes{pod=~"user-service.*", container="user-service"}

# Grafana에서 24시간 트렌드 확인
# 패턴: 시작 시 500MB → 점점 증가 → 1GB 도달 → OOM → 재시작 → 반복
# → 메모리 누수 의심!
```

**Step 4: 로그 분석**

```logql
# OOM 직전 로그
{namespace="production", pod=~"user-service.*"} 
| json 
| line_format "{{.timestamp}} {{.message}}"

# 특정 작업 반복 확인
{namespace="production", pod=~"user-service.*"} |= "cache" | json
```

**해결**:
```bash
# 임시 조치: 메모리 limit 증가
kubectl patch deployment user-service -n production -p '{"spec":{"template":{"spec":{"containers":[{"name":"user-service","resources":{"limits":{"memory":"2Gi"}}}]}}}}'

# 근본 해결: 메모리 누수 원인 코드 수정 (개발팀 협업)
```

## 📊 Part 3: 트러블슈팅 도구 정리

### 필수 쿼리 모음

```promql
# ===== 즉시 상태 확인 =====

# 에러율
sum(rate(http_requests_total{status=~"5.."}[5m])) by (service) / sum(rate(http_requests_total[5m])) by (service)

# P99 지연
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))

# CPU 사용률
sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) by (pod) / sum(kube_pod_container_resource_limits{resource="cpu"}) by (pod)

# 메모리 사용률
sum(container_memory_usage_bytes{container!=""}) by (pod) / sum(kube_pod_container_resource_limits{resource="memory"}) by (pod)

# Pod 재시작
sum(increase(kube_pod_container_status_restarts_total[1h])) by (pod) > 0

# ===== 근본 원인 추적 =====

# 노드별 리소스
100 - (avg by(instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# 디스크 사용률
(1 - node_filesystem_avail_bytes / node_filesystem_size_bytes) * 100

# 네트워크 에러
sum(rate(node_network_receive_errs_total[5m])) by (instance)
```
